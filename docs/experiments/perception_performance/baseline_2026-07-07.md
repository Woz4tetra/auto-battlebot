# Perception baseline: deployed models, 2026-07-07

Smoke test of the model_eval scoring pipeline against the in-progress hand-labeled test
dataset. This establishes the baseline numbers for the currently deployed detector models
before the full test dataset is labeled. Headline result: the keypoint model is in good
shape (recall 0.81 on our robot), but the blob model misses most opponent boxes
(opponent recall 0.34).

## Models scored

Both models from `config/_desktop.toml`, run together in one playback pass per SVO:

- Blob (YOLO-seg): `data/models/yolo26n-seg_nhrl_robots_2026-04-27_x86_64_sm89.engine`, confidence threshold 0.6
- Keypoint (YOLO-pose): `data/models/yolo26n-pose_our_robots_2026-05-01_x86_64_sm89.engine`

Caveat: these are the x86_64 desktop engines, not the aarch64 engines that run on the
Jetson. Same weights, different TensorRT builds. Treat this as the baseline for the model
weights, not a latency or Jetson-parity measurement.

## Ground truth

Snapshot of `training/data/nhrl_keypoints_eval_test` taken 2026-07-07 09:41 while
labeling was still in progress: 372 reviewed frames, of which 367 were covered by the
candidate runs and scored.

- 367 frames across 5 fight SVOs from the May 1-2 NHRL event
- 1018 boxes: 455 opponent, 354 mrs_buff_mk3, 202 house_bot, 7 object
- mr_stabs_mk2 does not appear in these fights
- Two more recordings (16-18-05, 17-26-12) are sampled but not yet labeled

Only frames marked reviewed in `.edit_state.json` were scored. `score.py` itself scores
every label file in the GT dir, so I built a filtered GT dir (symlinks) containing
reviewed frames only.

Scoring exclusions via taxonomy files:

- Blob: excluded `object` (the model has no object class; 7 boxes)
- Keypoint: excluded `opponent`, `house_bot`, `object` (the pose model only detects our
  robots), leaving the 354 mrs_buff_mk3 boxes

Per-class recall from the instance confusion matrix:

The failure mode is clear: opponent misses dominate. This matches the perception dropout
analysis from the May fights (opponent track live under 50% of frames). Precision is
decent (0.87 agnostic), so the cost is missed detections, not phantom robots.

## Pipeline issue found: playback drops frames

- Bug/Issue: with `svo_real_time_mode = false` (the eval_candidate default), the ZED
  capture thread grabs as fast as the SDK allows and the 40 Hz main loop only consumes
  the latest frame. Each pass covered only 25-39% of SVO frames, and `score.py` counts an
  uncovered GT frame as all false negatives. First pass matched 94/334 reviewed frames.
- Fix/Solution: `svo_real_time_mode = true` paces the grab at the recorded ~22 fps, below
  the loop rate. One real-time pass covered 99-100% of GT frames. I merged detections
  from all passes (fast and real-time, deduped by frame stamp) into one candidate MCAP
  per SVO before scoring; final coverage was 367/372.

Real-time pacing makes each run take the fight's wall-clock length (5-6 min per SVO).
A lockstep playback mode (process every frame, no pacing) would give full coverage at
full speed, but that is a code change to `ZedRgbdCamera`.

## Caveats

- Test dataset is roughly half done (372 of 622 sampled frames reviewed; 2 of 7
  recordings untouched). Numbers will move.
- x86 engines, not the Jetson aarch64 engines.
- GT labels were corrected from the same deployed models' pre-labels on different frames,
  so labeling is not fully independent of the models under test.

## Addendum, later on 2026-07-07: pipeline replaced, numbers superseded

The playback-based candidate recording described above is gone. `score.py` now runs
candidate engines directly on the GT images (shared inference code in
`auto_battlebot/trt_yolo.py`, same preprocessing and NMS as C++). One command per model,
seconds instead of hours, exact frame coverage by construction. The eval_candidate and
eval_smoke configs were removed; see `training/model_eval/README.md` for the current
workflow.

Direct-inference baseline on the same GT snapshot (372 reviewed frames):

| model | level | mAP50 | precision | recall | F1 |
|---|---|---|---|---|---|
| blob | agnostic | 0.664 | 0.943 | 0.675 | 0.787 |
| blob | instance | 0.620 | 0.818 | 0.586 | 0.683 |
| keypoint | agnostic | 0.844 | 0.939 | 0.852 | 0.893 |

Keypoint metrics: 9.6 px mean error, PCK@0.1 0.729, heading error 7.6 deg, heading
accuracy @10 deg 0.814.

These score higher than the playback numbers above (blob agnostic recall 0.675 vs 0.584,
keypoint kp_err 9.6 px vs 17.3 px) with the same engines and thresholds. For
model-vs-model comparisons, use the direct numbers; they are the baseline going forward.

Opponent recall remains the weak point in the direct numbers too: the instance confusion
matrix still shows the opponent class dominating the misses.

`training/model_eval/compare_cpp_python.py` reproduces the C++ (recorded playback) vs
Python (direct) comparison on demand and reports a linear fit between matched detections
from the two paths.

## Root cause of the C++ vs Python gap: playback rectification warp

- Bug/Issue: the 2x keypoint pixel-error gap (17.3 px playback vs 9.6 px direct) looked
  like a C++ postprocess bug. It is not. Matched C++/Python detection pairs differ by a
  shared affine warp (x scale 1.027, y scale 1.017, offset -6 to -10 px) that applies to
  boxes and keypoints alike, and ECC alignment of the *images themselves* (live-recorded
  frame vs desktop-playback frame of the same SVO frame) shows the same warp (x scale
  1.023-1.027, y 1.014-1.024). The ZED SDK rectifies the SVO slightly differently on the
  desktop than the live Jetson run did (SDK version or per-SN calibration file
  difference). GT was labeled on live pixels, so playback detections carry a systematic
  ~13 px offset against it. `yolo_keypoint_model.cpp`'s math is correct; its letterbox,
  decode, and scale-back match the Python implementation exactly.
- Fix/Solution: none needed in C++. The direct-inference eval path runs on the live
  pixels and is immune. Do not score desktop-playback detections against live-labeled GT
  (and more generally, desktop SVO replays do not reproduce live Jetson frames
  pixel-exactly).

This also explains most of the playback-vs-direct detection deltas: every playback box
was shifted ~13 px in x against GT, which costs borderline IoU matches at the 0.5
threshold, on top of the compression differences between the two image sources.
