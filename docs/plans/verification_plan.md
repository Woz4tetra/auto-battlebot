# Verification plan

Goal: every change in this repo, mine or an agent's, arrives with machine-checked evidence that it
works end to end. A change is done when the checks for its tier pass, not when its author says so.

The decisions come from a grilling session on 2026-11-15. The full question and answer log is in
[Decision log](#decision-log) at the end.

## What went wrong

Two failure modes drove this plan:

- **Silent behavior change.** The EdgeTX transition broke CRSF telemetry. Driving still worked and
  the filter muscled through on perception alone, so nothing looked wrong. No check asserted that
  telemetry was arriving.
- **Hardware changes declared working without running on hardware.** Firmware and link changes
  can't run on the dev box, and nothing distinguishes "builds" from "verified on the robot".

## Requirements

- Every suite runs from one entry point, and the stop hook runs the affected part of it on every
  turn that touches code.
- Bug fixes start with a test that fails on the current code. Features land with their tests in the
  same commit.
- "Tested" is tiered by what the code touches:
  1. Pure logic (C++, Python): unit test
  2. Pipeline behavior: lockstep playback regression against a stored baseline
  3. Firmware and hardware: host-side unit test where the logic allows, plus a step in the guided
     HIL session
  4. UI and dashboard: browser check with a screenshot
- Every link in the loop has a declared rate. A configured link that goes silent is a failure in
  playback, sim, HIL, and on the live dashboard.
- Every feature is listed with how the user reaches it and the check that proves it from there.
- An independent agent reviews each non-trivial change before it counts as done.
- No hardware rig is bought. HIL runs on demand with a human driving.

## Phases

Each phase is usable on its own. Phase 5 is mostly physical and can run in parallel with 3 and 4
whenever the Jetson is on the bench.

### Phase 0: every suite green

- Add `scripts/verify`, which runs C++ gtest, pytest (`tests/python/`, `training/synthetic/tests/`),
  `pio test -e native` for `firmware/mr_stabs_mk2`, and `npm run check`.
- Run it and fix every failing test before any other phase starts. No quarantine.
  - Stale test (behavior changed on purpose): fix the test, cite the commit that changed it.
  - Real bug: show the test failing, fix, show it passing.
  - Unclear: collect into one list for the user before touching any of them.

### Phase 1: gates on the agent loop

**`scripts/verify` tiers:**

| Flag | Runs | Budget |
| --- | --- | --- |
| `--fast` | lint, incremental build, affected gtest, pytest, firmware native | ~90 s |
| `--changed` | picks suites from a file list instead of running all | |
| `--playback` | lockstep clips (phase 3) | |
| `--realtime` | real-time playback tier (phase 3) | |
| `--sim` | nav plan 3.5 lockstep smoke tier | ~7 min on x86 |
| `--hil <host>` | guided session (phase 6) | ~5 min |

**Touched-files log.** A PostToolUse hook on Write/Edit appends each path to
`.claude/state/touched-<session>.txt` (gitignored). The stop hook and verifier pick suites from
this list, never from the whole working diff. The user co-edits this tree; their uncommitted
files are not the agent's to test or fix.

**Stop hook.** Replaces `lint --quick` with `scripts/verify --fast --changed` over the touched-files
list. A failure blocks the stop.

**Verifier agent.** `.claude/agents/verifier.md`.

- Input: the diff and the original user request, not the implementer's summary.
- Can read code, run any `scripts/verify` tier, and run specific tests. Cannot edit files.
- Checks:
  - Missing tests for the change's tier
  - Claims in the turn that the diff doesn't support
  - **Mutation check:** in a scratch worktree, revert the change's non-test hunks and run the new
    tests. If they still pass, they prove nothing, and the verdict is FAIL.
  - Code and its golden fixture or baseline changed in the same diff: FAIL unless the turn states
    a reason the verifier agrees with. No `--bless` flag; the verifier is the gate.
  - New or changed features carry a feature-map proof (phase 4), from the start of phase 4.
- Output: PASS or FAIL with findings, in `.claude/state/verdict-<diffhash>.json`.
- A Stop hook blocks the stop when the touched files include `src/`, `include/`, `firmware/`,
  `auto_battlebot/`, or `tests/` and no verdict exists for the current diff hash. Docs and plan
  edits pass.
- On FAIL the implementer fixes and re-runs. After two FAILs on the same finding, stop and bring it
  to the user.

### Phase 2: liveness

Amends nav plan 1.4 (`PerformanceMonitor`). Its single `Link` row becomes a per-link table:

| Link | Measured as |
| --- | --- |
| Camera frames | frame rate and age |
| Perception output | result rate |
| Filter output | output rate |
| Transmit | command send rate |
| CRSF telemetry rx | frame rate and age |
| ESP-NOW | ack rate and command age |
| IMU | sample rate and age |
| Relay publish | publish rate |

- Expected rate and max age per link are defaulted fields in the config struct.
- A configured link that is silent past its max age is red, not a warning.
- First test cases: the CRSF-after-EdgeTX case, the 22-09 calibration problem, and the phantom
  `neutral_robot_1`.
- `scripts/verify_mcap <file>` runs the same checks offline over any recording. Every bench or
  field session that comes back gets graded.
- `crsf` and `health` get unit tests first: frame parse/encode round trips against captured EdgeTX
  telemetry bytes, and the staleness logic. `channels`, `simulation`, and `viz_relay` start as
  feature-map gaps.

### Phase 3: deterministic playback

Playback today differs run to run:

| Source | Where |
| --- | --- |
| SDK skips frames when the pipeline is slow | `svo_real_time_mode = true`, `config/playback/_playback.toml:72` |
| 250 Hz control loop on wall time; latest-value handoff | `ThreadedControlLoop`; `control_loop.cpp:48-51`, `128-132` |
| Clock adds wall time since the frame | `CameraFollowingClock`, `camera_following_clock.hpp:29-45`; feeds filter `predict`, staleness, RL observation ages, playback transmitter init delay |
| Sleep pacing | `max_loop_rate_hz = 60`, `runner.cpp:622-641` |

TensorRT is not a source: static shapes, one stream per engine, synced before host reads. There is
no unseeded RNG in `src/`; PCL RANSAC is believed to default to a fixed seed (unverified).

**Lockstep tier.** `config/playback/_lockstep.toml`:

- `svo_real_time_mode = false`, `max_loop_rate_hz = 0`, `SteppedControlLoop`
- A new stepped clock that advances one control period per cycle. Under `ManualClock`,
  `SteppedControlLoop::advance_to` gives every catch-up cycle the same `now`, so the filter never
  coasts between frames.
- First task: run a clip twice and diff the output MCAP topics. If they differ, find what is left
  (the ZED SDK's depth and positional tracking are the open unknown).
- Gate: output topics hash identical per machine class, plus metric baselines for cross-machine
  comparison.

**Clips.** 3-4 clips of about 60 s, one per eval recording. Metrics: opponent and our-robot track
coverage, jump rate, nav command summary, liveness checks.

**Real-time tier.** Today's mode, kept because lockstep can't see timing bugs. Scored on loop
latency p95, frame-drop rate, and liveness. Tolerance per metric comes from 5 runs on the same code
(A/A spread). Baselines per machine class.

**Sim.** `scripts/verify --sim` runs the nav plan 3.5 smoke tier. The deleted sim sweep (5af3d75)
is not restored.

### Phase 4: feature map

`docs/features.toml`, one entry per feature:

- `name`
- `reach`: how the user reaches it (dashboard command, transmitter switch, config key, CLI)
- `code`: paths
- `proofs`: gtest names, pytest ids, playback/sim/HIL check names
- `supporting`: unit tests of internals

A proof must exercise the feature from its `reach`. "ESP-NOW substitution under SA" needs a check
that flips the SA channel value and observes the substituted command; a unit test of the packer is
supporting only.

- Bootstrap: draft entries from `include/remote/protocol.hpp` commands, transmitter channels,
  factory `type`s, and CLIs; the user reviews.
- Backfill proofs in a dedicated phase. From its start, any new or changed feature must already
  carry its proof (verifier check).
- `scripts/lint` enforcement switches on in the commit that closes the last gap: it fails when a
  feature has no proof or a listed proof doesn't exist.
- `scripts/lint` renders the map to a diagram page: features, how they're reached, what proves
  them.

Add a local web-based interactive UI to explore the graph and gain insight about each component.

### Phase 5: CI

The repo is public, so no runner is attached to GitHub. A tailnet-only forge mirrors it.

**Forge.** Forgejo as a home-apps service on genericservername:

- `forgejo` service in `~/home-app/docker-compose.yml` (official image, SQLite, data in
  `data/forgejo`)
- `handle_path /forgejo/*` block and bare-path redirect in `caddy/Caddyfile`; `ROOT_URL` set to the
  tailnet `/forgejo/` URL; a landing-page tile
- Registration disabled; one account
- SSH published on the tailnet IP only, port 2222
- Added as a second push URL on `origin`, so `git push` updates GitHub and Forgejo together:

```bash
git remote set-url --add --push origin ssh://git@<genericservername-tailnet-ip>:2222/<user>/auto-battlebot.git
```

The existing GitHub runner in `~/actions-runner` on genericservername (GenericWebsiteName) is
unrelated and left alone.

**Runner.** The spare Orin NX:

- Reflashed to JetPack 6.2.3 / L4T R36.5 with the ZED SDK, matching the ZED Box Mini
- No cameras attached; the ZED SDK decodes SVOs without one
- `forgejo-runner` in host mode as a dedicated unprivileged `ci` user: fresh checkout per job, no
  sudo, no secrets, no route to the dashboard cable network (10.42.42.0/24)
- No x86 runner

**Data.** CI clips are stored on the Jetson's disk, synced once from the dev box, and checked
against a content-hashed `ci_clips` manifest at job start. Engines are built on the Jetson's own
TensorRT 10.3 by a setup job, cached by ONNX hash plus TensorRT version, never copied between
boxes.

**Schedule.**

| When | Runs |
| --- | --- |
| Every push | `--fast` (all suites), `--playback` |
| Nightly | `--realtime`, `--sim` |
| On demand | `--hil` |

**Deploy.** `scripts/deploy_to_jetson.sh` asks Forgejo for the commit's status and warns when it
isn't green. It does not refuse.

**Report-back.** The agent pushes only when asked. After a requested push it waits for the
Forgejo run and reports pass/fail with links to failed steps; a red run reopens the task. Needs a
read-only Forgejo token on the dev box.

### Phase 6: guided HIL session

`scripts/verify --hil <host>`:

1. Deploy to the host.
2. Prompt the user through a fixed checklist: arm, drive forward 2 s, spin, flip SA, toggle each
   switch.
3. Record an MCAP.
4. Run `verify_mcap` plus per-step assertions (e.g. after "flip SA", the ESP-NOW substitution flag
   changes within 200 ms).

The script never sends autonomous drive commands; the user drives. HIL runs on demand only.
