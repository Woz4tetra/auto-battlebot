Cut code comments by 99%, stop new ones from landing, and replace the TOML comments that currently
stand in for "what values is this profile loading" with a config system that shows the effective

## Why

Comments let a hack carry its own defense. An agent writes a workaround, adds "otherwise X breaks",
and the next agent reads the warning and preserves the workaround instead of fixing the cause. The
justification survives every refactor because nothing checks it.

The config files have the same problem one level up. A profile's comments describe values that a
base file or a struct default may have changed since, and `--print-config` omits struct defaults,
so the comments are the only place an operator looks and they are not authoritative.

Where each kind of "why" goes instead:

| Content | Destination |
| --- | --- |
| Why a change was made | Commit message (`git blame` keeps the link) |
| An invariant ("must stop recording before reboot") | A test, or a type/name that makes the wrong use impossible |
| A measurement, eval result, fitted value provenance | Dated report under `docs/` or `docs/experiments/` |
| What a block of code does | A function with that name |
| Units and meaning of a config field | The field name (`max_motor_rpm_per_s`) and the resolved-config view |
| A register layout or timing from a part datasheet | `DATASHEET:` comment, the one surviving prose exception |
| History ("previously", "no longer") | Nowhere. `git log` has it |
| Plan checkpoints ("step 3", "Phase 2") | Nowhere |

## The rule

Goes into `CLAUDE.md` under Conventions, replacing the comment guidance scattered through Writing:

- Don't write code comments. That covers `//`, `/* */`, `#`, TOML comments, and Python docstrings
  longer than one line.
- One-line docstrings are allowed and do not count.
- Put the reason for a change in the commit message. Put measurements in a dated doc. Turn an
  invariant into a test. Turn a block that needs explaining into a named function.
- If a workaround needs a comment to survive review, it needs a test or a fix instead.
- Exempt without counting: machine directives (see [Exempt forms](#exempt-forms)) and
  `DATASHEET:` comments in the required format.
- Generated files and vendored code are excluded from the check entirely.

### Exempt forms

These count zero and carry no prose:

| Form | Constraint |
| --- | --- |
| `#!` shebang | First line only |
| `#pragma`, include guards | Preprocessor, not comments |
| `// NOLINT(check-name)`, `// NOLINTNEXTLINE(check-name)` | Check name required, no trailing prose |
| `# noqa: CODE` | Code required, no trailing prose |
| `# type: ignore[code]` | Code required, no trailing prose |
| `// clang-format off` / `on`, `# fmt: off` / `on` | Generated or table data only |
| `# -*- coding` and SPDX / license headers | First 5 lines only |
| `<!-- prettier-ignore -->` and similar formatter directives | Formatter directive only |

The no-trailing-prose constraint matters: `# noqa: E501 because the URL can't wrap` is a
justification and counts.

### DATASHEET marker

The one prose exception. Allowed anywhere, expected almost only in `firmware/` and `hardware/`.
Format, enforced by the checker:

```cpp
// DATASHEET: BNO055 rev 1.4, table 4-2: OPR_MODE NDOF = 0x0C
// DATASHEET: ESP32-S3 TRM v1.2, 7.4.3: RMT carrier duty is in APB ticks
```

```python
# DATASHEET: AS5600 rev 1.06, p. 18: ANGLE register is 12 bits, MSB at 0x0E
```

- `DATASHEET:` then a document identifier with revision, then a locator (`table N`, `N.N.N`,
  `p. N`, `fig. N`), then a colon and the fact.
- One line per fact. A multi-line `DATASHEET` block is a sign the code should be a named constant
  table instead.
- The fact must come from the document. Bench measurements, "the ESC clamps at 6.5%", and anything
  learned by trial are not datasheet facts and go to `docs/`.
- The checker rejects `DATASHEET:` lines that lack the revision or locator.

## Enforcement (phase 0)

Lands before any deletion, so the count can only go down from the moment it exists.

### `scripts/comment_budget.py`

A standalone CLI, in `scripts/` since it is a single-file tool.

- Inputs: `git ls-files`, minus an exclude list kept in the script: `data/`, `third_party/`,
  `firmware/BlHeli-Passthrough/`, `.pio/`, `node_modules/`, generated files
  (`web/**/protocol.ts`, `firmware/velocity_jig/include/splash_anim.h`, anything with a
  `@generated` or `DO NOT EDIT` first-line marker).
- Extraction per language:
  - C, C++, TS, JS, `.ino`: a small lexer that skips string, char, and raw-string literals, then
    takes `//` and `/* */`. Each physical line of a block comment counts once.
  - Python: `tokenize` for `#` comments, `ast` for docstrings (module, class, function). A docstring
    counts as its line count when that is 2 or more, else 0.
  - Shell, TOML, CMake, `.ini`, YAML: `#` lines outside quoted strings.
  - Markdown is not checked. `docs/` is where prose belongs.
- Classifies each line as counted, exempt directive, or `DATASHEET`. Malformed `DATASHEET` lines
  fail immediately regardless of budget.
- Baseline file: `.comment-baseline.json`, checked in, `{path: count}`. Files absent from it have a
  budget of 0.
- Modes:
  - `check` (default): fails if any file's count exceeds its baseline. Prints each offending file,
    its new count, its budget, and the offending lines with line numbers.
  - `check --files a b c`: same, limited to the given paths. Used by the hook.
  - `ratchet`: rewrites the baseline down to current counts. Never raises a value. Drops entries
    that hit 0.
  - `report`: totals by directory and language, and the top 30 files, for tracking progress.
  - `blocks --json`: every counted block with path, line range, and text. Feeds the audit.
- Renames: a file whose path is new but whose content `git diff -M` pairs with a baselined path
  inherits that budget. Without this, moving a file would fail the check.
- Unit tests in `tests/python/` cover the lexer edge cases: `//` inside strings, URLs in strings,
  raw strings, nested quotes in shell, `#` inside TOML strings, docstring vs. plain string
  expression.

### The checker checks itself

`scripts/comment_budget.py` is subject to its own rule, with a budget of 0.

- It is not on the exclude list and never gets a baseline entry. Its tests and any fixture files
  get a budget of 0 as well.
- Its own source has no counted comments: one-line docstrings only, exempt directives only where a
  tool requires one.
- Test fixtures that contain comments (lexer cases, `DATASHEET` examples) are string literals inside
  the test file, never loose fixture files, so they are not counted.
- A test asserts that `scripts/comment_budget.py`, its test file, and the hook wrapper are all in the
  scanned file set, and that `check --files scripts/comment_budget.py` passes. If someone adds the
  script to the exclude list or gives it a baseline entry, the test fails.
- A second test copies the script into a temp git repo, appends one `#` comment, and asserts `check`
  fails on it. This proves the self-check is live and not just passing because the file is skipped.
- The same applies to the hook wrapper (if the hook needs a shell shim) and to any changes to
  `scripts/lint` made in P0.2. `scripts/lint` already carries 93 comment lines, so P0.2 may not
  add to that count.

### Wiring

- `scripts/lint`: runs `comment_budget.py check` in both full and `--quick` modes (it is fast), then
  `ratchet` only when not `--dry-run` and the check passed. Ratcheting inside lint means deletions
  are recorded without anyone having to remember.
- `.claude/settings.json`: a second `PostToolUse` hook on `Write|Edit`, next to
  `no_ai_slop_check.sh`, running `comment_budget.py check --files <edited file>`. The agent sees
  the failure on the edit that caused it. The hook reads the edited path from the hook JSON on
  stdin, the same way `no_ai_slop_check.sh` does.
- Pre-commit: same as the lint check, so a human commit that bypasses the agent hooks still fails.
- No `--allow` flag and no inline opt-out marker. An escape hatch becomes the new place to write
  justifications. A file that truly needs a higher budget gets its baseline entry edited by hand,
  which shows up in the diff.

### CLAUDE.md

- Add [The rule](#the-rule), the exempt forms, and the `DATASHEET` format.
- Delete the per-field comment habit from the config guidance (see phase 3).
- Under Writing, the "code comments" mention changes to "commit messages and docs"; code comments no
  longer exist to be written well.

Phase 0 is done when `scripts/lint` passes on `main` with the baseline equal to the measured counts,
the hook fires on an Edit that adds a comment, `comment_budget.py` passes its own check at a budget
of 0 with the self-check tests green, and `CLAUDE.md` states the rule.

## Audit (phase 1)

Every counted block gets a verdict before anyone deletes it. Deleting a fence comment without
checking whether it guards something real is how this project would cause regressions.

Input: `comment_budget.py blocks --json`, about 8,400 blocks plus docstrings.

Verdicts:

| Verdict | Meaning | Action in phase 2 |
| --- | --- | --- |
| `DELETE` | Restates code, banner, history, plan reference, stale | Delete |
| `RENAME` | Code needs the comment because a name is vague | Rename variable/function/field, delete comment |
| `EXTRACT` | Comment heads a block that does one thing | Extract named function, delete comment |
| `TEST` | States an invariant or a failure mode | Write a test that fails if violated, delete comment |
| `TYPE` | States a precondition a type could enforce (units, non-null, range) | Strong type or validation, delete comment |
| `DOC` | Measurement, eval result, provenance of a tuned value, design rationale worth keeping | Move to a dated doc, delete comment |
| `HACK` | Comment justifies a workaround | File in the hack ledger (below), leave the comment until fixed |
| `DATASHEET` | Cites a part document | Rewrite into the `DATASHEET:` format |
| `CONFIG` | TOML comment, or a config-struct field comment | Handled by phase 3 |

The `HACK` verdict produces the most valuable output of the whole project: a list of every
workaround the codebase currently defends with prose. That list goes in
`docs/plans/comment_purge_hack_ledger.md`, one row per hack:

| Column | Content |
| --- | --- |
| Location | `path:line` |
| What the code does | One sentence |
| What the comment claims would break | One sentence |
| Verified? | Whether the auditor reproduced the claim (test, replay, or reading the code path) |
| Root-cause fix | The change that makes the workaround unnecessary, or "none known" |

Method:

- Split by area, one auditor per area (see [Work packages](#work-packages)). Per-area CSVs go to a
  scratch directory, never `runs/` (training outputs only) and never `data/`. The merged verdict
  file lands as `docs/plans/comment_purge_audit.csv` so phase 2 packages can be handed out from it.
- Auditors read the surrounding code, not only the comment. A `TEST` or `HACK` verdict needs the
  auditor to state the concrete failure, or it gets downgraded to `DELETE`/`DOC`.
- Fence comments (`never`, `do not`, `otherwise`, `must`) are never `DELETE` without a reason
  written in the CSV.
- Spot-check: I review a random 5% of `DELETE` verdicts per area before phase 2 starts on it. Any
  area with more than 2 wrong verdicts in the sample gets re-audited.
- This is the step that needs a multi-agent run; about 8 agents, one per area. It needs an explicit
  go-ahead.

Phase 1 is done when every counted block has a verdict, the hack ledger exists, and the spot-checks
pass.

## Removal (phase 2)

Executed per area, one commit per area per verdict type, so a bad batch reverts cleanly.

Order inside each area:

1. `DELETE` and banner removal. Pure deletions, no behavior change. Build and test after.
2. `RENAME` and `EXTRACT`. Mechanical refactors; build, test, and `./scripts/lint`.
3. `DOC`. Write the doc first, then delete the comment in the same commit, so the fact is never
   only in git history. Measurements go in a doc named for what was measured with the date
   (`docs/experiments/2026-10-15_sysid_wheel_radius.md`), not one catch-all file.
4. `TEST` and `TYPE`. Write the test, watch it fail with the guarded behavior removed, restore,
   delete the comment. If the test cannot be written in under an hour, move the item to the hack
   ledger.
5. `DATASHEET` rewrites.
6. `HACK` items are not touched in phase 2. Each one is fixed separately from the ledger. When its
   root cause is fixed, the workaround and its comment go together.

Rules while removing:

- The tree is shared with the user's own edits. Format and lint only the files changed in the
  commit, never run a repo-wide formatter.
- Do not touch `docs/pseudo_code.md`.
- Commit messages for `TEST`/`TYPE`/`DOC` commits name the comment's old claim, so `git log -S`
  still finds it.
- Playback regression after the `src/` and `include/` packages: run `/replay` on the standard
  recordings and compare against a run from before the package. Any diff in commands sent is a bug
  in the removal, since phase 2 changes no behavior except where a `TEST` verdict forced a fix.
- `./scripts/lint` ratchets the baseline down on every pass, so progress is visible in
  `.comment-baseline.json` diffs.

Phase 2 is done when every non-`HACK`, non-`CONFIG` block is gone and the replay check shows no
command diff.

## Config system (phase 3)

The TOML comments exist because nobody can see what a profile loads. Deleting them without fixing
that makes things worse, so this phase builds the visibility first and deletes the comments last.

### Problems in the current system

Measured from `src/config/config.cpp` and the 39 top-level and ~22 subdirectory TOML files:

1. **Defaults are invisible.** `load_merged_config` returns only keys the files set.
   `--print-config` prints that merged table and says so in its own header. Struct defaults, which
   `CLAUDE.md` asks us to rely on ("leave a config key out when its value matches the struct
   default"), never appear anywhere an operator looks.
2. **No provenance.** The merged table does not say which file in the `extends` chain set a value.
   Finding where `max_motor_rpm` comes from means reading every file in the chain by hand.
3. **Type change wipes the section.** `merge_into` replaces a table wholesale when `type` differs.
   That is correct for the fields, but it forces every profile that swaps an implementation to
   restate every field. Ten config files carry a comment explaining this ("the type differs from
   _common, so the merge replaces this section and every field is restated").
4. **Copy-paste sections.** Eight sections of 4+ keys appear verbatim in more than one file. The
   largest:
   - `[plant]`, 16 keys, identical in 5 files (`mr_stabs_mk2_desktop`, `mr_stabs_mk2_jetson`,
     `playback/mr_stabs_mk2_playback`, `simulation/mr_stabs_mk2_kinematic_sim`,
     `simulation/mr_stabs_mk2_kinematic_sim_sensing`), and a
     second 16-key `[plant]` shared by `mr_stabs_mk2_aer_zed_box` and `mr_stabs_mk2_fid_zed_box`
   - `[transmitter]`, 9 keys, shared by `mr_stabs_mk2_aer_zed_box` and `mr_stabs_mk2_fid_zed_box`
   - `[keypoint_model]`, 10 keys, shared by the sysid zed box and sysid playback profiles
   - `[field_filter]`, 7 keys, shared by `mr_stabs_mk2_fid_zed_box` and
     `mrs_buff_mk3_fid_rl_zed_box`
   When one copy is updated and the others are not, two profiles for the same robot drive with
   different plants, and nothing reports it.
5. **Single inheritance only.** A profile is robot × platform × venue × experiment, but `extends`
   takes one parent. The chain encodes one axis and the others get copied.
6. **Units live in comments.** `max_motor_rpm_per_sec = 2000  # RPM/s; normalized 1.33/s` and
   `velocity_saturation_limit = 1.0  # 0 = disabled`. The field name or the type has to carry this.

### Target

Three properties, in priority order:

1. **Every loaded value is visible with its source.** For any profile, one command prints every
   field every component reads, its value, and where it came from: a file and line, or the struct
   default.
2. **Each fact is written once.** A robot's plant, a transmitter setup, a venue's field geometry
   each live in one file, and profiles compose them.
3. **Effective config changes show up in review.** A change to `_common.toml` that alters 14
   profiles shows 14 profile diffs in the PR, not one line.

### Step 3a: resolved config with defaults and provenance

- `ConfigParser` already sees every field each component parses (it throws on unrecognized
  fields). Extend it to record, per field read: section path, key, final value, and source. Source
  is either `default` or the file and line that set it last.
- Provenance needs the merge to carry source info. `merge_into` keeps a side map
  `{toml path -> (file, line)}` populated from `toml::node::source()`, which toml++ already tracks.
- The parse step runs every factory's config parse without constructing components (no camera, no
  TensorRT), so it is safe on a dev box for any profile, including Jetson-only ones.
- `--print-config` changes to print the fully resolved config: every field, defaults included,
  annotated. Output format is TOML so it can be diffed and reloaded:

  ```toml
  [transmitter]
  type = "EspNowTransmitter"                 # mr_stabs_mk2_fid_zed_box.toml:21
  max_motor_rpm = 1500                       # mr_stabs_mk2_fid_zed_box.toml:30
  max_motor_rpm_per_s = 2000                 # mr_stabs_mk2_fid_zed_box.toml:31
  failsafe_timeout_s = 0.25                  # default
  ```

  This is generated output, so the source annotations are not code comments and the checker
  ignores `config/resolved/`.
- The app records the same resolved table into each MCAP at startup (one message on a
  `/config/resolved` topic, schema documented in `docs/foxglove_recording_format.md`). Every
  recording then says exactly what it ran with, which also fixes "which plant was this run on"
  questions in replay analysis.
- The web dashboard gets a read-only resolved-config view for the active profile, fed by the same
  table.

### Step 3b: checked-in snapshots

- `config/resolved/<profile>.toml`: one generated file per profile (every non-underscore TOML),
  produced by `--print-config`.
- A GoogleTest regenerates every snapshot in memory and fails on a diff, with the command to
  update them in the failure message. `./scripts/lint` regenerates them (it already regenerates
  `protocol.ts`).
- With snapshots checked in, the "leave a key out when it matches the default" convention stays:
  the snapshot shows the default, so omitting it no longer hides it. A struct default change now
  shows up as a diff in every affected snapshot.

### Step 3c: remove duplication

Two candidate mechanisms; pick one in review:

- **Option A, fragments (recommended).** A profile lists `includes = ["plants/mr_stabs_mk2_geometry",
  "transmitters/espnow_mr_stabs", "venues/aer"]` alongside `extends`. Fragments live in
  `config/fragments/<kind>/` and each holds the sections for one fact. Merge order: `extends` chain
  first, then each include in listed order, then the profile's own keys. The checker fails if two
  includes set the same key (no silent last-wins between fragments; the profile itself may
  override). Fixes problems 4 and 5 without changing how `extends` works.
- **Option B, generated profiles.** One `config/profiles.py` (or TOML matrix) declares robot,
  platform, venue, and experiment axes and generates every profile. Strongest dedupe, but the TOML
  files become build outputs, and the user edits a generator to change a value. Heavier than the
  problem needs.

Also in this step:

- Type-change replacement (problem 3) stays, since inherited fields from another implementation are
  meaningless. Fragments make it cheap: the swapped-in section comes from a fragment, not a restated
  copy. Delete the ten "every field is restated" comments as each section moves.
- Units into names (problem 6): rename fields whose meaning sits in a trailing comment, for example
  `max_motor_rpm_per_sec` to `max_motor_rpm_per_s`. "0 = disabled" sentinels become
  `std::optional` (absent = disabled). Every rename is one commit with the TOML, struct, and
  snapshot changes together. Old key names fail at parse with "renamed to X", since the parser
  already rejects unknown keys.
- `profiles.toml` and other standalone configs get the same treatment: their comments go, and the
  regex `pattern` gets a test listing which profiles it must match and must exclude.

### Step 3d: delete TOML and config-struct comments

Only after 3a and 3b land. Every `CONFIG` verdict from the audit gets one of:

- deleted, because the snapshot now shows the value and source
- moved to a doc, for fitted-value provenance (the `[plant]` derivation in
  `mr_stabs_mk2_fid_zed_box.toml` goes to `docs/plant_backed_control.md` or a sysid report)
- turned into a field rename or validation rule

The same applies to field comments in `include/**/config.hpp` and `*_config.hpp`, which is most of
why those headers are 45-64% comments.

Phase 3 is done when `--print-config` shows defaults with provenance for every profile, snapshots
are checked in and tested, no section of 4+ keys appears verbatim in two files, and `config/` has
zero counted comments.

## Error message essays (phase 4)

A comment ban pushes justification into string literals. Some already exist: the
`ConfigValidationError` in `DeadReckoningMotionEstimatorConfiguration::apply_plant` is a paragraph.

- Error and log messages state what is wrong, the value, and what to change. One sentence.
  "requires a [plant] table; none found in the extends chain of mr_stabs_mk2_jetson" is enough.
- Anything longer belongs in a doc, and the message may name the doc.
- Not enforceable by the comment checker. A lint rule in `comment_budget.py report` lists string
  literals over 160 characters inside `throw`, `spdlog::`, `raise`, and `logging.` calls, for
  review. It reports and does not fail.
- Same rule for `help=` strings in Python CLIs and CLI11 descriptions: one line.

## Lock-down (phase 5)

- Baseline left over: `HACK` ledger items and `DATASHEET` lines (which count zero anyway). Target
  total under 180 counted lines, which is 1% of 18,026.
- Ledger items get fixed one at a time. Each fix deletes the workaround and its comment together.
- Once the baseline is under 180, `comment_budget.py` prints the remaining lines in `report` so they
  stay visible.
- Revisit in 3 months: if nothing has been added and the ledger is empty, delete the baseline file
  and make the check "zero counted comments" outright.

## Risks

- **Deleting a fence that guarded something real.** Mitigation: fences are never `DELETE` without a
  written reason, `TEST` verdicts require a failing-then-passing test, and the playback replay
  check runs after the `src/` and `include/` packages.
- **Knowledge loss.** Some comments hold the only record of a measurement. Mitigation: `DOC`
  verdicts write the doc in the same commit as the deletion, and commit messages quote the old
  claim so `git log -S` finds it.
- **Justification migrates to strings, names, or commit-free hacks.** Phase 4 covers strings. Names
  like `workaround_for_zed_bug()` are visible in review, which is better than a comment. Hacks
  without comments are no worse than today, and now the ledger exists to compare against.
- **Merge conflicts with the user's concurrent edits.** Mitigation: small per-area commits, no
  repo-wide formatting, and the user is told which area is in flight.
- **Provenance plumbing in toml++.** `source()` gives line numbers per node, but the merge copies
  nodes, which may drop source regions. If so, the side map is filled before copying. Check this
  first in P3a.
- **Snapshot churn.** A default change rewrites many snapshots. That churn is the point (it shows
  every affected profile), but snapshots must be regenerated by lint so nobody hand-edits them.

## Open questions

1. Fragments (option A) or generated profiles (option B) for P3c? The plan recommends A.
2. Should test files follow the full rule, or may a test keep a one-line comment naming the
   recording or bug it reproduces? The plan assumes the full rule; the test name carries that.
3. `hardware/` is 1,218 lines of Python comments in CAD scripts. Does dimension provenance there
   (why a hole is 3.2 mm) count as `DATASHEET` when it comes from a part drawing? The plan says yes
   if the drawing has a part number and revision, otherwise `DOC`.
4. Should the MCAP `/config/resolved` topic be one message at start, or re-published on runtime
   config changes (opponent count, target override)? Those are runtime state, not config, so the
   plan assumes start only.
5. Unit renames break any external script that reads profile TOML by key. Are there consumers
   outside this repo?
